0. Verdict in five lines
--------------------------------------------------------------------------
- It works. 39/39 tests pass (17 s), PROOF.bend prints ALL PROOFS CHECK (0.3 s),
  all three examples run and print what the README shows, CSV output is
  byte-identical to Polars' write_csv on the fixture, and my own 10 optimizer
  traps all gave "optimised == unoptimised" results.
- Coverage of Polars is narrow but the covered subset is correct and
  Polars-checked. Roughly 10-15 % of the Polars expression/API surface.
- Code quality is high for Bend; the design docs are unusually honest.
- The laws are real proofs, not tautologies, but they prove schema/shape facts,
  not that the engine computes the right rows. About a third are one-step unfolds.
- Worth continuing as an experiment and as a hub package; it is not a Polars
  replacement and the string representation caps performance until it changes.

  with_columns that REPLACES `a`, then filter on `a`      -> filter not pushed (correct)
  select that swaps `a` and `e` via aliases, filter a>0   -> renamed to e>0 below (correct)
  Head over Filter over Head                              -> neither head moves (correct)
  Head over WithColumns over Sort                         -> head sinks to the sort, stops (correct)
  select of a literal only                                -> keeps one source column for height (correct)
  filter on a group key above GroupBy                     -> not pushed (conservative, correct)
  select(n) over with_columns(n = a*2)                    -> projection keeps `a` (correct)
  filter on `a` where select aliases `c` as `a`           -> rewritten to c > 1 (correct)
  two filters, inner reads the new column                 -> split correctly
  left join, is_null(right col), head                     -> untouched (correct)

2. Test coverage
--------------------------------------------------------------------------
39 golden-output test files, 1136 expected lines, all checked against Polars 2.0
where a Polars analogue exists (the test headers say which; sort/groupby/join
tests were generated by Bend and diffed against Polars with maintain_order).

Covered well:
  - dtype/scalar/err formatting; I32 vendored arithmetic (div/mod/read ranges)
  - kernels (map/zip/fold/compact/gather/iota, Kahan sum)
  - columns from scalars with nulls, head/slice/clone/gather/compact
  - CSV: quotes, escaped quotes, CRLF, empty fields, inference, strict dtypes,
    IO errors as values, round trip, fixture parse, goldens at 4 decimals
  - Expr typing: every row of the typing table and its mismatches, cast table
  - Eval: arithmetic per dtype with nulls, wrap-around, div by zero, casts
    (incl. lenient str->number), Kleene and/or, is_null/fill_null, filter on
    null predicate, aggregations with nulls / all-null / empty, early errors,
    duplicate output names
  - Sort: multi-key, desc, nulls first/last, stability witnessed by a row id,
    NaN/-0.0/inf, i32, bool, str, one row, no rows
  - GroupBy: null key group, every AggOp per dtype, multi-key, f32 keys with
    NaN and -0.0, expression keys, empty, one row, maintain_order=False
  - Join: multi-key, differing right key names, i32 keys with nulls both
    sides, many-to-many, bool/f32 keys (0.0 == -0.0, NaN == NaN), empty sides,
    null-slot invariant, `_right` suffix, early errors
  - Plan.schema early errors; optimizer: 8 plan shapes compared raw vs optimised
  - Facade: the whole public surface once
  - describe: nulls, i32, str, bool, all-null, one-row std, nearest-rank quantiles
  - Six end-to-end goldens byte-identical to Polars (at float_precision=4)

Gaps (none of these are tested):
  - Correctness at scale lives only in the bench harness (bench/check.py,
    run by scripts/bench.sh), not in `make test`. q1/q2/q4/q5 at 1M rows were
    reported identical; I did not rerun the 10-minute bench.
  - No property/randomised tests; everything is hand-picked small frames.
  - No test that lazy and eager agree for every verb on the same data (the
    optimizer test compares lazy raw vs lazy optimised; eager is tested apart).
  - write_csv is tested through a real file once; no quoting test for output
    with strings containing the separator (the code path exists).
  - The "too many rows" cap (2^23 rows per Array.new of a boxed default,
    DESIGN 12.7) has no test; a >8M-row Str column is unexplored.
  - No negative tests of the proof file beyond the one the implementer did by
    hand (DESIGN 8 says a false claim fails; not kept as a test).
  - u32 overflow in `sum` is untested (Polars wraps too, so probably fine).

Grade: good for a 10k-line prototype; it is a golden-output suite, so it
freezes current behaviour rather than specifying it. A single-file
"differential vs Polars" generator (random frames, run both, diff) would be
worth more than most of the remaining hand tests.

3. How much of the Polars 2.0 API is implemented?
--------------------------------------------------------------------------
Polars 2.0 (release post): streaming engine by default, row order not
guaranteed unless maintain_order=True, out-of-core spilling, SQL as a
first-class interface, new Map dtype and map.* expressions, strictness and
collect_schema() as the way to catch schema mismatches early, join
reordering, CSE, dynamic predicates/Bloom filters.

What bend-frame took from 2.0 specifically: the strictness stance (no implicit
casts, collect_schema resolves before any read, same error from collect and
collect_schema) and the maintain_order flag (present, ignored: order is
always first-appearance, which is the stricter behaviour). Nothing of
streaming, out-of-core, SQL, Map, CSE, join reordering.

Rough tally against Polars' surface:
  dtypes        5 of ~25  (Bool U32 I32 F32 Str; no 64-bit, no dates, lists,
                structs, categorical, decimal, map, binary, null)
  verbs         select, with_columns, filter, sort, head, group_by, inner/left
                join, describe, read/scan/write csv, explain, collect_schema.
                Missing: outer/semi/anti/cross/asof joins, unique, drop,
                rename, tail, slice, reverse, explode, pivot/unpivot, concat,
                window/over, rolling, join_where, parquet/ipc/json, sql, etc.
  expressions   col, 6 typed lits, alias, cast, + - * / %, neg, 6 comparisons,
                and/or/not, is_null/is_not_null/fill_null, 9 aggregations.
                Missing: everything in .str, .dt, .list, .struct namespaces,
                when/then/otherwise, is_in, is_between, clip, abs, round,
                pow, log/exp, cum_*, shift, rank, over, quantile, std/var as
                expressions, etc. Aggregations only inside group_by (eager
                broadcasts them in select; lazy refuses them).
  Estimate: 10-15 % of the expression and verb surface; maybe 40 % of what a
  typical small ETL script uses.

The Elixir Explorer alternative was not pursued; the Polars shape was chosen
and the README says so.

--------------------------------------------------------------------------
4. Quality
--------------------------------------------------------------------------
Strong points:
  - Clear layering (dtype/err/kernels/column/schema/expr/eval/sort/groupby/
    join/csv/fmt/plan/exec/facade), each module header restates its contract
    and its idioms. Helper-above-caller, no mutual recursion, every reused
    binder marked `+`; the Bend restrictions are followed consistently.
  - Errors are values everywhere (ResT), lazy and eager share the same checks
    (Plan.schema calls Join.schema and Grp.validate), so they cannot drift.
  - The plan interpreter and the expression evaluator are compiled to postfix
    code and run by one loop: a sound choice for Bend's termination checker.
  - Engineering of the hot paths is real: LSD radix argsort on order-
    preserving words, dictionary-coded strings for group_by, open-addressing
    hash join on flat arrays, exact f32 decimal formatting (round half even,
    verified against Python on random values).
  - DESIGN.md 14 and IMPLEMENTING.md record deviations and pitfalls honestly;
    bench/README.md explains where the time goes rather than hiding it.
Weak points:
  - Volume: ~16k lines (10k library) for this surface, 2-3x a conventional
    implementation, as DESIGN 12.1 predicted. The eval dispatcher is a large
    (op x dtype) table; adding a dtype touches many places.
  - A Frame is linear: a Source frame is consumed by one Source node, so a
    self-join or reusing the same env frame twice in a plan fails with
    InvalidOperation. Users must clone explicitly. Not in the README's
    "Differences from Polars" list; it should be.
  - `read_csv` infers types from a sample; a lazy ScanCsv fixes the schema at
    scan time from the first rows, then Exec re-reads strictly and fails if a
    later row disagrees. Fine, but the error surfaces only at collect.
  - Facade ergonomics: every eager step needs a `match r: case Fail / Done`
    wrapper (see tests/facade.bend); there is no `and_then` helper. A
    `DF.then(r, f)` would halve user code.
  - probes/ (22 programs) and build/ artifacts are in the repo; probes are
    documentation now, fine, but build/ should stay ignored (it is, mostly).

--------------------------------------------------------------------------
5. Bugs and divergences found
--------------------------------------------------------------------------
No crash, hang or wrong-row bug found in the implemented subset. Divergences
from Polars that are silent (no error, no note in README) and that I would
call bugs under the project's own "strict, no silent changes" goal:

  B1. Integer `div` by zero answers 0, `mod` by zero answers the left operand.
      Polars: `a // 0` is null, `a / 0` is a float inf (and `/` always
      returns Float64). Only a test comment mentions it. Should be null.
  B2. Cast F32 -> U32 of a negative or out-of-range value answers 0 silently
      (cast(-1.5) = 0, cast(1e12) = 0). Polars' strict cast raises
      InvalidOperation; non-strict gives null. Should be null or an error.
  B3. `div` on integer columns keeps the integer dtype (truncating). In Polars
      `/` is true division to Float64 and `//` is the integer one. The README
      says "arithmetic keeps a numeric dtype" as if it were a feature; a
      Polars user writing qty / 2 gets a different answer. Document loudly or
      add `floordiv` and make `div` require f32.
  B4. `mean` of integers is F32 (Polars Float64): documented. At 1M rows an
      f32 mean of 32-bit ids loses digits; Kahan helps the sum, not the width.
  B5. group_by `sum` over F32 is a plain sequential add; 1.3e-5 relative error
      at 1M rows vs Polars' 3e-7. The agent kept it so the 20-row golden matches
      Polars to the last digit. Polars' own lazy group_by sum is sequential too
      (IMPLEMENTING.md "Goldens"), so this is arguably faithful, but the
      README should not advertise "byte-identical" for q3 beyond 1k rows.
  B6. The eager `filter(a > mean(a))` is accepted by eager (broadcast) but the
      lazy layer refuses any aggregation outside group_by. Lazy and eager
      disagree on which programs are valid. Documented in plan.bend only.
  B7. Join output always drops the right key, also when left_on/right_on
      differ. Polars 2.0 does the same (coalesce default), so not a bug, but
      the README's join section does not say what happens to the right key.
  B8. Source frames used twice in one plan (self-join) fail at collect with
      "source not in env (or used twice)". Schema resolution accepts the plan,
      so collect_schema says OK and collect fails: that violates the project's
      own "collect refuses what collect_schema refuses, and only that" claim.

Minor:
  - `lit_i32(v: U32)` takes the bit pattern; `lit_i32(3000000000)` is silently
    negative. A range check would cost nothing.
  - U32 `+`/`*` wrap silently (Polars wraps too; Polars 2.0 strict mode does
    not check this either). Fine, but worth one README line.
  - "Error: TypeMismatch in gt: expected u32, got f32" for a > mean(a) is
    correct but reads as if mean were wrong; a hint about casting would help.

6. Are the laws sane, or tautologies?
--------------------------------------------------------------------------
Short answer: real, mechanically checked, but modest in what they say.

How the proofs are built. Bend's checker accepts `{==}` when both sides
compute to the same normal form; `%e : P` rewrites with an equation; Done/
Some injectivity and Fail/Done refutation are built with motives and
Empty.absurd; induction is structural recursion with the IH passed as a
lambda. There is no `@unsafe`, no admitted lemma, no foreign code. I checked
PROOF.bend end to end; every `def Laws.x` matches the `law x` statement.

Classification of the 48 laws:
  (a) One-step unfolds, 14 laws: project_nil, dtype_eq_refl, alias_name,
      col_name, alias_type, alias_is_agg, agg_is_agg, col_refs, lit_type,
      col_type, is_null_type, is_not_null_type, source_schema,
      head_keeps_schema. These are `{==}` after at most one rewrite. They are
      true by definition of the code: tautological in the sense that they
      cannot fail unless someone edits the code. Their value is as
      regression pins (if `alias` ever stops naming its expression the proof
      file fails), not as discoveries.
  (b) Case-analysis laws, 11: cmp_type_bool, arith_type, mod_type,
      logic_type, cast_type, counting_type, keeping_agg_type, sum_type,
      mean_type, filter_keeps_schema, sort_keeps_schema, select_cols_is_
      project. Each enumerates every constructor of BinOp/AggOp/DType and
      refutes the impossible ones. Not deep, but they genuinely rule out a
      whole class of typing-table typos (a wrong row in Expr.type.bin.ok
      breaks the proof).
  (c) Inductive laws with real content, 15: project_length, project_names,
      with_existing_keeps_width, with_new_appends, filter_schema_is_input,
      sort_schema_is_input, select_cols_names, with_column_keeps_width,
      head_pass_keeps_schema, merge_pass_keeps_schema, merge_head_keeps_
      schema, merge_pass_merges, merge_fixed_point, merge_idempotent,
      head_pass_merges. These are inductions over lists/plans with inversion
      lemmas (chk_inv, done_inj, and_filter, unary/binary). merge_fixed_point
      and merge_idempotent in particular are the kind of thing that catches
      a real optimizer bug (a pass that keeps rewriting).
  (d) Shape laws over linear arrays, 5: head_len, head_dtype,
      mask_not_slots, mask_and_slots, iota_slots. Non-trivial because arrays
      are affine and every lemma has to hand the rewritten array back as a
      Sigma witness. They model Array.size with a pure `slots` function;
      the model is sound by inspection of Base.
  (e) Arithmetic, 2: i32_add_comm (lifts Base's U32.add_comm), i32_bits_
      roundtrip (unfold).
  (f) One law, no_adjacent_filters/no_adjacent_heads post-conditions: these
      use the law file's own predicates, defined by the same recursion as
      the pass. Reasonable, but note the predicate and the pass were written
      by the same hand; a bug shared by both would pass.

What is NOT proven, and matters more than what is:
  - Nothing about execution. No law says Filter keeps only true rows, Sort
    is stable, group_by sums are sums, or a join matches keys. All 48 laws
    live in the schema/plan/shape layer. "48 laws proved" in the README is
    accurate but a reader may take it as engine correctness; it is not.
  - The optimizer is proven schema-preserving only for 2 of its 4 passes
    (merge, head). Predicate pushdown and projection pushdown, the two
    passes that can actually change results if wrong, have no proof at all,
    and none about result equivalence for any pass. DESIGN 8 says why
    (String.eq has no computational proof in Base). The blocker is real
    but it means the headline "optimizer soundness" is a test, not a proof.
  - head_keeps_schema is trivial, but head_pass_keeps_schema (over the
    whole pass with a pending limit) is real.
  - The `Opt.merge` law needs the well-typed hypothesis because on ill-typed
    plans the error message changes (documented); fine.

Sanity: I re-ran the negative test myself (slots laws changed to 2^(d+1)):
Bend's checker rejects it with the expected/observed terms, with or without
--verdict. --verdict (the independent BendTT kernel built with Lean 4.34.0)
accepts the real PROOF.bend. A tests/proof_negative.bend that expects
SOME PROOFS FAIL would keep this honest (the test runner already
special-cases that string).

Verdict on the laws: sane, honest, correctly scoped in the docs, and about
one third ceremonial. They are a good foundation for a hub package whose
pitch is "schema-checked dataframes", not evidence that the engine is right.

7. Are the shortcomings addressable?
--------------------------------------------------------------------------
Performance (13-100x slower than Polars at 1M, 9-48x single-thread):
  - Strings as cons lists are the dominant cost (CSV parse 5 s for 41 MB,
    group_by key coding ~150 ms, string compare ~95 ns/row). Addressable:
    dictionary-encode Str columns at parse time (U32 codes + a small
    dictionary) or hold them as byte arrays. This is a representation
    change inside column.bend/csv.bend/sort/groupby/join and touches the
    whole string path, but the design already codes strings per query, so
    the code is prepared for it. Expect 3-10x on string-heavy queries and
    most of the parse time back. Medium effort (days, not weeks).
  - No kernel is forked (Kernel.fork_depth is a constant 0); 12 cores give
    1.0-2.1x. Addressable in principle, but DESIGN 12.5 measured <=1.8x
    intra-column speedup on this machine, so the ceiling is low; cross-
    expression parallelism in with_columns is the cheaper win.
  - Sort+head as top-k: easy, isolated in sort.bend.
  - Freeing a 1M-row frame costs ~300 ms because of linear strings: goes
    away with the representation change.
  - The gap will not close to 1x. Bend's affine arrays, 32-bit-only
    numerics and no SIMD mean a realistic target is "within 3-5x of
    single-thread Polars on numeric queries", which the q2 numbers (9x,
    unforked) suggest is reachable.
Semantics:
  - B1, B2, B8 are one-afternoon fixes (null on div-by-zero and failed
    cast; count Source uses in Plan.schema).
  - B3 (div dtype) is a one-line decision plus a floordiv constructor.
  - F64/I64: Bend has no 64-bit numeric primitive; I64 could be vendored
    like I32 over a pair of U32 but F64 cannot. This is a hard limit of the
    platform, not of the project: means stay f32 forever.
Proofs:
  - Pushdown schema laws are blocked on a String.eq reflexivity lemma in
    Base. If Char equality is primitive and opaque to the checker, the
    lemma is unprovable inside Bend; the honest path is to state it as an
    axiom-like law in Base or to change Names.has to a decidable-equality
    structure the checker can unfold. Not in this project's hands.
  - Execution-level laws (filter length <= n, sort permutes) need models of
    the kernels like `slots`; the array-witness pattern in PROOF.bend scales
    to them but each is a few hundred lines of proof. Possible, expensive.
  - --verdict: done in this review (elan + leanprover/lean4:v4.34.0);
    add it to `make proofs` now that it runs in under a second.
Surface:
  - Each missing expression (is_in, when/then, str.len, abs, ...) is one
    typing row plus one eval kernel; cheap individually. Window functions,
    unique, rename, drop, tail, slice, concat: all small. Dates/lists/
    structs: a new dtype each, expensive given the (op x dtype) tables.

8. Worth more work? Publish to hub.bend-lang.com?
--------------------------------------------------------------------------
Publish: yes, as 0.1.x, provided three things are done first, because a hub
publish is public and permanent:
  1. Fix B1/B2/B8 (silent wrong values and the collect_schema/collect
     mismatch), add B3/B7/the linear-Source rule to "Differences from
     Polars" in README.
  2. Soften the README claims: "byte-identical to Polars" is true at 20 and
     1k rows and for q1/q2/q4/q5 at 1M; say that. "48 laws" should be
     followed by one sentence saying they are schema/shape laws, and that
     optimizer result-equivalence is tested, not proven.
  3. Add a differential test generator against Polars (bench/.venv already
     exists) so the next contributor cannot silently break null semantics.
Also decide B5 (compensated group sum vs matching Polars' lazy sum); I would
keep the sequential add, since Polars' streaming engine does the same, and
say so.

Worth more work: as an experiment, clearly yes. It is the largest coherent
Bend program I have seen with proofs, a benchmark and a Polars-checked test
corpus, and the design/implementing notes make it a useful reference for
anyone writing Bend. The value is in: (a) the schema-checked lazy API as a
showcase of Bend's law/proof system, and (b) the measured record of where
Bend loses to Rust. As a dataframe library people would use for data work,
not yet: the surface is too small, strings are too slow, there is no F64,
and the facade is verbose. The three ranked next steps in the README
(string representation, top-k, parallel kernels) are the right order; I
would put "differential tests + the B-list fixes" before all of them.

If the goal is "how far can Bend go", the string representation is the
experiment to run next; if it is the hub, publish after the README and
semantic fixes above and treat performance as a 0.2 story.
